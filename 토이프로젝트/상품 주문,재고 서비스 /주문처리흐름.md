## 주문 처리 흐름

주문은 접수 → 재고 확보 → 주문 확정 → 알림 생성 순서로 처리한다.

사용자가 주문을 요청했을 때 바로 반환하는 결과는 ‘접수 완료’이다. 실제 주문 확정 여부는 재고를 확인한 뒤 결정한다.

아래에서는 사용자가 상품 A를 2개 주문한 상황을 예로 설명한다.

### 1 주문 접수

| 순서 | 담당 모듈 | 처리 내용 |
|---|---|---|
| 1 | 주문 API | 사용자에게 상품 A 2개를 주문하는 요청을 받는다. |
| 2 | 주문 API | 같은 요청을 이미 접수했는지 주문 DB에서 확인한다. 이미 접수했다면 기존 주문을 반환한다. |
| 3 | 상품 API | 주문 API의 요청을 받아 상품 DB에서 상품 A의 현재 가격과 판매 상태를 확인한다. 이때 Redis 캐시는 사용하지 않는다. |
| 4 | 주문 API | 판매 가능한 상품인지, 수량이 올바른지 확인하고 주문 금액을 계산한다. |
| 5 | 주문 API | 주문 DB에 주문을 ‘처리 중’으로 저장한다. 같은 DB 트랜잭션에서 Outbox에도 ‘상품 A 2개를 확보해 달라’는 내용을 저장한다. |
| 6 | 주문 API | DB 저장이 성공하면 사용자에게 주문 ID와 ‘처리 중’ 상태를 반환한다. |

Outbox는 Kafka로 보낼 내용을 보관하는 DB 테이블이다. 주문과 Outbox는 함께 저장되거나 함께 취소되도록 처리한다.

이 단계에서는 주문이 접수된 것이며, 재고 확보와 주문 확정은 아직 끝나지 않은 상태이다.

### 2 재고 확보 요청 전달

| 순서 | 담당 모듈 | 처리 내용 |
|---|---|---|
| 1 | 주문 이벤트 발행 | 주문 DB의 Outbox에서 아직 보내지 않은 내용을 찾는다. |
| 2 | 주문 이벤트 발행 | Kafka로 ‘이 주문의 상품 A 2개를 확보해 달라’는 메시지를 보낸다. |
| 3 | 주문 이벤트 발행 | Kafka 전송 성공을 확인하면 Outbox에 전송 완료를 표시한다. |
| 4 | 재고 이벤트 처리 | Kafka에서 해당 요청을 읽는다. |

주문 API가 재고 처리 프로그램을 직접 호출하는 방식은 아니다. Kafka에 요청을 남기면 재고 처리 프로그램이 읽어서 처리한다.

### 3 재고 확인과 확보

상품 A의 보유 수량이 10개이고, 다른 주문을 위해 이미 확보한 수량이 3개라고 가정한다.

| 항목 | 수량 |
|---|---|
| 보유 수량 | 10개 |
| 기존 예약 수량 | 3개 |
| 추가 주문 가능 수량 | 7개 |
| 이번 주문 수량 | 2개 |

| 순서 | 담당 모듈 | 처리 내용 |
|---|---|---|
| 1 | 재고 이벤트 처리 | 같은 요청을 이미 처리했는지 재고 DB에서 확인한다. |
| 2 | 재고 이벤트 처리 | 다른 주문과 동시에 수량을 잘못 변경하지 않도록 해당 재고에 접근하는 순서를 DB에서 제어한다. |
| 3 | 재고 이벤트 처리 | 주문 가능한 7개 중 2개를 이번 주문용으로 확보한다. |
| 4 | 재고 이벤트 처리 | 재고 DB에 주문별 예약 내역을 저장하고 예약 수량을 3개에서 5개로 변경한다. |
| 5 | 재고 이벤트 처리 | 같은 DB 트랜잭션에서 처리 기록과 ‘재고 확보 성공’ Outbox를 저장한다. |
| 6 | 재고 이벤트 처리 | DB 저장이 성공하면 Kafka에 해당 메시지의 처리 완료 위치를 기록한다. |

처리 후 보유 수량은 10개, 예약 수량은 5개, 추가 주문 가능 수량은 5개이다.

여기서 확보는 실제 출고가 아니라 ‘다른 주문에서 사용하지 못하도록 수량을 예약하는 것’을 의미한다.

### 4 재고 확보 결과 전달과 주문 확정

| 순서 | 담당 모듈 | 처리 내용 |
|---|---|---|
| 1 | 재고 결과 발행 | 재고 DB의 Outbox에서 ‘재고 확보 성공’ 결과를 읽는다. |
| 2 | 재고 결과 발행 | Kafka로 성공 결과를 보내고, 전송 성공 후 Outbox에 완료를 표시한다. |
| 3 | 주문 결과 처리 | Kafka에서 성공 결과를 읽는다. |
| 4 | 주문 결과 처리 | 주문 DB에서 같은 결과를 이미 처리했는지, 현재 주문이 처리 중인지 확인한다. |
| 5 | 주문 결과 처리 | 주문을 ‘확정’으로 변경한다. 같은 DB 트랜잭션에서 처리 기록과 ‘주문 확정’ Outbox를 저장한다. |
| 6 | 주문 결과 처리 | DB 저장이 성공하면 Kafka에 해당 메시지의 처리 완료 위치를 기록한다. |

이 시점부터 사용자가 주문 상태를 조회하면 ‘확정’으로 확인된다. 알림 생성은 이후 별도로 진행한다.

### 5 사용자 알림 생성

| 순서 | 담당 모듈 | 처리 내용 |
|---|---|---|
| 1 | 주문 이벤트 발행 | 주문 DB의 Outbox에서 ‘주문 확정’ 내용을 읽어 Kafka로 보낸다. |
| 2 | 주문 이벤트 발행 | 전송 성공을 확인하고 Outbox에 완료를 표시한다. |
| 3 | 알림 이벤트 처리 | Kafka에서 주문 확정 결과를 읽고 중복 처리 여부를 확인한다. |
| 4 | 알림 이벤트 처리 | 알림 DB에 ‘주문이 확정되었습니다’라는 알림과 처리 기록을 함께 저장한다. |
| 5 | 알림 이벤트 처리 | DB 저장이 성공하면 Kafka에 해당 메시지의 처리 완료 위치를 기록한다. |
| 6 | 알림 API | 사용자가 알림을 조회하면 알림 DB에서 본인의 알림을 읽어 반환한다. |

알림 처리가 늦어지더라도 이미 확정된 주문이 실패로 바뀌지는 않는다.

### 6 재고가 부족한 경우

상품 A의 주문 가능 수량이 1개인데 사용자가 2개를 주문한 경우이다.

| 순서 | 담당 모듈 | 처리 내용 |
|---|---|---|
| 1 | 재고 이벤트 처리 | 재고 DB를 확인하고 수량이 부족하다고 판단한다. 재고는 변경하지 않는다. |
| 2 | 재고 이벤트 처리 | 재고 DB에 실패 사유·처리 기록·‘재고 확보 실패’ Outbox를 함께 저장한다. |
| 3 | 재고 결과 발행 | 실패 결과를 Outbox에서 읽어 Kafka로 보낸다. |
| 4 | 주문 결과 처리 | Kafka에서 실패 결과를 읽고 주문 DB의 상태를 ‘실패’로 변경한다. 실패 사유·처리 기록·‘주문 실패’ Outbox를 함께 저장한다. |
| 5 | 주문 이벤트 발행 | 주문 실패 결과를 Kafka로 보낸다. |
| 6 | 알림 이벤트 처리 | 실패 결과를 받아 알림 DB에 주문 실패 알림과 처리 기록을 저장한다. |
| 7 | 주문·알림 API | 사용자에게 주문 실패 상태와 사유, 실패 알림을 각각 조회해 제공한다. |

각 발행 모듈은 전송 성공 후 Outbox에 완료를 표시한다. 각 이벤트 처리 모듈은 DB 저장 성공 후 Kafka에 처리 완료 위치를 기록한다.

여러 상품을 한 번에 주문했다면 모든 상품의 수량을 확보할 수 있을 때만 예약한다. 하나라도 부족하면 일부 상품만 예약하지 않고 전체 확보를 실패 처리한다.

### 7 주문을 취소하는 경우

아래 흐름은 ‘확정된 주문만 취소할 수 있다’는 제안을 기준으로 한다. 취소 가능 조건은 구현 전에 확정한다.

| 순서 | 담당 모듈 | 처리 내용 |
|---|---|---|
| 1 | 주문 API | 주문 DB에서 주문 소유자와 취소 가능 상태를 확인한다. |
| 2 | 주문 API | 주문을 ‘취소 처리 중’으로 변경하고, 같은 DB 트랜잭션에서 ‘이 주문의 예약 수량을 반환해 달라’는 Outbox를 저장한다. |
| 3 | 주문 API | 사용자에게 취소 요청 접수 결과를 반환한다. 아직 취소 완료는 아니다. |
| 4 | 주문 이벤트 발행 | Outbox의 재고 반환 요청을 Kafka로 보낸다. |
| 5 | 재고 이벤트 처리 | Kafka에서 요청을 읽고, 재고 DB에서 해당 주문용으로 예약한 상품 A 2개를 해제한다. 처리 기록·반환 성공 Outbox를 함께 저장한다. |
| 6 | 재고 결과 발행 | 반환 성공 결과를 Kafka로 보낸다. |
| 7 | 주문 결과 처리 | 결과를 읽고 주문 DB의 상태를 ‘취소 완료’로 변경한다. 처리 기록·주문 취소 Outbox를 함께 저장한다. |
| 8 | 주문 이벤트 발행 | 주문 취소 완료 결과를 Kafka로 보낸다. |
| 9 | 알림 이벤트 처리 | 결과를 받아 알림 DB에 취소 완료 알림과 처리 기록을 저장한다. |
| 10 | 주문·알림 API | 사용자가 조회하면 취소 완료 상태와 알림을 반환한다. |

재고 예약을 해제하면 해당 수량은 다시 다른 주문에서 사용할 수 있다. 보유 수량 자체를 늘리는 것은 아니다.

재고 반환에 실패하면 주문을 취소 완료로 변경하지 않는다. 실패 사유를 남기고 재요청하거나 운영 확인 대상으로 처리한다.

### 8 중간에 장애가 발생한 경우

| 장애 상황 | 처리 방식 |
|---|---|
| 상품 정보 확인 실패 | 주문 접수를 완료하지 않고 오류를 반환한다. |
| 주문 DB 저장 실패 | 접수 성공을 반환하지 않는다. 주문과 Outbox는 함께 저장되거나 함께 취소된다. |
| Kafka 전송 실패 | 보낼 내용이 Outbox에 남아 있으므로 다시 전송한다. |
| Kafka 전송 후 Outbox 완료 표시 전에 중단 | 같은 메시지가 다시 전송될 수 있다. 받는 모듈에서 처리 기록으로 중복 반영을 막는다. |
| 이벤트 처리 중 DB 저장 실패 | Kafka에 처리 완료 위치를 기록하지 않고 다시 처리한다. |
| DB 저장 후 Kafka 처리 완료 위치 기록 전에 중단 | 같은 메시지를 다시 받아도 기존 처리 기록을 확인해 재고·주문·알림을 중복 변경하지 않는다. |
| 알림 처리 지연 | 주문 상태는 유지하고 알림 처리를 재시도한다. |
