## 실행과 연결

| 항목 | 내용 |
|---|---|
| 소속 이미지 | `inventory-service` |
| 실행 역할 | HTTP API |
| 배포 단위 | `Deployment`: `inventory-api` |
| 업무용 Service | 필요 |
| 연결 대상 | 재고 DB |
| 입력 | HTTP 입고·재고 조회 요청 |
| 출력 | 재고 정보 또는 입고 결과를 HTTP로 반환한다. Redis·Kafka를 직접 사용하지 않는다. |

## 구현할 기능

| 기능 | 처리 내용 |
|---|---|
| 입고 등록 | 권한과 수량을 확인하고 재고 수량·입고 이력을 함께 저장한다. |
| 중복 입고 방지 | 입고 요청 식별값을 확인해 수량을 두 번 늘리지 않는다. |
| 재고 조회 | 보유·예약·주문 가능 수량을 원본 DB에서 조회한다. |
| 예약 조회 | 상품별·주문별 예약 내역을 조회한다. |

## 실패·복구 설계

입고와 예약이 동시에 진행돼도 수량이 틀리지 않도록 한다. 실제 출고는 후속 범위이며, 반환은 보유 수량 증가가 아닌 예약 해제이다.

## Kubernetes 파일 계획

다음 이름의 파일을 설계 후 k8s 폴더에 작성한다. 현재 파일을 생성하거나 설정값을 확정한 상태는 아니다.

- `deployment.yaml`
- `service.yaml`
- `configmap.yaml`
- `serviceaccount.yaml`

인증정보는 Secret 참조 방식을 정한 뒤 연결한다. 실제 비밀값을 저장소에 넣지 않는다. 복제 수·Probe·requests/limits·종료 처리·배치·확장·통신 정책은 이 모듈의 설계 단계에서 정한다. Worker의 모니터링용 Service가 필요하면 업무용 Service와 구분해 추가한다.

## 구현 전 정할 것

- 요청·응답 또는 이벤트 구조와 오류 처리 기준.
- DB 테이블·트랜잭션·중복 방지 방식.
- 연결 설정과 비밀·권한 전달 방식.
- 실행 명령·상태 점검·종료 방식.
- 정상·배포·장애·복구 검증 항목.

## 실행·검증 방법

구현 후 실제 명령과 확인 결과를 기록한다. 현재 실행 가능한 프로그램과 적용 가능한 YAML은 없다.
