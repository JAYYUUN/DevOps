# 상품 주문·재고 서비스 설계

## 1. 서비스별 구현 범위

| 서비스 | 구현할 기능 | 직접 관리할 데이터 |
|---|---|---|
| 상품 서비스 | 상품 등록·수정·판매 중지, 상품 목록·상세 조회, 조회 캐시 관리 | 상품명·설명·가격·판매 상태 |
| 주문 서비스 | 주문 접수, 주문 목록·상태 조회, 재고 처리 결과 반영, 주문 취소, 실패·미완료 주문 조회 | 주문·주문 상품·주문 상태 |
| 재고 서비스 | 입고 등록, 재고 조회, 주문 수량 예약, 예약 실패 처리, 취소 시 예약 해제 | 재고 수량·주문별 예약 내역 |
| 알림 서비스 | 주문 확정·실패·취소 이벤트 처리, 사용자 알림 목록·읽음 처리, 발송 실패 관리 | 사용자 알림·처리 상태 |

알림 기능의 첫 범위는 서비스 안에서 조회하는 알림을 저장하고 제공하는 것이다. 이메일·문자 전송은 이후 확장 대상으로 둔다. 초기 알림 실패 관리는 이벤트 처리와 알림 저장 실패의 확인·재시도를 의미한다.

## 2. 배포 모듈별 역할

모듈은 Kubernetes에서 별도로 배포하고 실행하는 프로그램 묶음이다.

각 모듈의 DB는 해당 서비스가 관리하는 DB를 의미한다. 다른 서비스의 DB에 직접 접근하지 않고 API 또는 Kafka로 통신한다.

| 모듈 | 역할 | 구현할 기능과 데이터 흐름 | Kubernetes 구성 |
|---|---|---|---|
| 상품 API | 상품 관리·조회 창구 | 상품 등록·수정·판매 중지는 상품 DB에 반영한다. 수정·판매 중지 시 Redis의 해당 상품 캐시를 삭제한다. 상세 조회는 Redis를 먼저 확인하고, 없으면 상품 DB에서 조회한 뒤 Redis에 저장한다. 목록 조회는 상품 DB를 사용한다. | Deployment + Service |
| 주문 API | 주문 접수·조회 창구 | 주문 접수 시 상품 API로 원본 가격·판매 상태를 확인한다. 주문과 재고 확보 요청 Outbox를 주문 DB에 함께 저장한다. 주문 조회는 주문 DB를 사용한다. 취소 접수 시 주문 상태와 재고 반환 요청 Outbox를 함께 저장한다. Kafka로 직접 전송하지 않는다. | Deployment + Service |
| 주문 결과 처리 | 주문 상태 변경 | Kafka에서 재고 확보·반환 결과를 읽는다. 주문 DB에서 중복 여부와 현재 상태를 확인한다. 주문 상태·처리 기록·최종 결과 Outbox를 함께 저장한다. DB 처리 성공 후 Kafka 소비 위치를 기록한다. | Deployment |
| 주문 이벤트 발행 | 주문 관련 내용 전달 | 주문 DB의 미발행 Outbox를 읽어 재고 확보 요청·반환 요청·주문 최종 결과를 Kafka로 전송한다. 전송 성공 시 주문 DB에 발행 완료를 기록하고, 실패하면 재시도 정보를 저장한다. | Deployment |
| 재고 API | 재고 관리·조회 창구 | 입고 요청을 검증하고 재고 DB의 수량과 입고 이력을 함께 저장한다. 같은 요청의 중복 반영을 방지한다. 재고·주문별 예약 내역은 재고 DB에서 조회한다. | Deployment + Service |
| 재고 이벤트 처리 | 재고 확보·반환 | Kafka에서 재고 확보·반환 요청을 읽는다. 재고 DB에서 중복 여부와 수량을 확인한다. 재고 변경·처리 기록·결과 Outbox를 함께 저장한다. DB 처리 성공 후 Kafka 소비 위치를 기록한다. | Deployment |
| 재고 결과 발행 | 재고 처리 결과 전달 | 재고 DB의 미발행 Outbox를 읽어 확보·반환 성공 또는 실패 결과를 Kafka로 전송한다. 전송 성공 시 재고 DB에 발행 완료를 기록하고, 실패하면 재시도 정보를 저장한다. | Deployment |
| 알림 API | 사용자 알림 조회 창구 | 알림 DB에서 본인의 알림 목록과 미확인 개수를 조회한다. 읽음 처리 시 소유자를 확인하고 알림 DB의 상태를 변경한다. | Deployment + Service |
| 알림 이벤트 처리 | 사용자 알림 생성 | Kafka에서 주문 확정·실패·취소 완료 결과를 읽는다. 알림 DB에서 중복 여부를 확인하고 알림과 처리 기록을 함께 저장한다. DB 처리 성공 후 Kafka 소비 위치를 기록한다. | Deployment |

### 데이터 처리 기준

- Redis는 상품 상세 조회 캐시로 사용한다.
- 주문·재고·알림의 업무 데이터와 처리 기록은 각 서비스의 DB에 저장한다.
- Outbox는 Kafka로 전달할 내용을 보관하는 DB 테이블이다.
- 업무 데이터 변경과 Outbox 저장은 하나의 DB 트랜잭션으로 처리한다.
- Kafka 이벤트가 다시 전달될 수 있으므로 받는 모듈에서 중복 처리를 방지한다.
- Worker는 Kafka·DB에 직접 연결하므로 업무 요청을 받기 위한 Service가 필요하지 않다.

### 주요 용어

| 용어 | 의미 |
|---|---|
| API | 사용자나 다른 프로그램의 요청을 받고 결과를 반환하는 접점이다. |
| Deployment | 프로그램의 실행 개수와 버전 교체 등을 관리하는 Kubernetes 자원이다. |
| Service | 실행 중인 API Pod에 접근할 고정된 주소와 트래픽 전달 경로를 제공하는 Kubernetes 자원이다. |
| Kafka | 프로그램 사이에서 처리할 내용과 결과를 전달·보관하는 통로이다. |
| 이벤트 | 주문 접수, 재고 확보 성공 등 발생한 사실이나 처리할 내용을 전달하는 메시지이다. |
| Outbox | Kafka로 전달할 내용을 업무 데이터와 함께 DB에 저장하는 방식이다. |

처리·발행 모듈은 외부 HTTP 요청을 받지 않고 백그라운드에서 동작한다. 표의 Service 여부는 업무 요청을 받기 위한 기준이며, 모니터링 등의 목적으로 추가될 수 있다.

## 3. 주문 처리 흐름

사용자가 상품 2개를 주문하는 경우의 처리 흐름이다.

| 순서 | 담당 모듈 | 처리 내용 |
|---|---|---|
| 1 | 주문 API | 주문을 DB에 저장하고 사용자에게 접수 결과를 반환한다. |
| 2 | 주문 이벤트 발행 | Kafka로 해당 주문의 상품 2개를 확보하도록 요청한다. |
| 3 | 재고 이벤트 처리 | 재고를 확인하고 상품 2개를 해당 주문용으로 확보한다. |
| 4 | 재고 결과 발행 | Kafka로 재고 확보 성공 결과를 전달한다. |
| 5 | 주문 결과 처리 | 주문 상태를 처리 중에서 확정으로 변경한다. |
| 6 | 주문 이벤트 발행 | Kafka로 주문 확정 결과를 전달한다. |
| 7 | 알림 이벤트 처리 | 사용자에게 보여줄 주문 확정 알림을 저장한다. |
| 8 | 주문·알림 API | 사용자가 조회하면 주문 상태와 알림을 반환한다. |

재고가 부족하면 재고 확보 실패 → 주문 실패 → 실패 알림 순서로 진행한다.

주문 API의 첫 응답은 접수 결과이다. 주문 확정 여부는 재고 확인 후 결정한다.

## 4. 상품 API 모듈

상품 정보의 원본은 MariaDB에 저장한다. Redis는 자주 조회하는 상품 정보를 임시 보관하는 캐시로 사용한다.

| 기능 | 처리 내용 |
|---|---|
| 상품 등록 | 관리자가 입력한 상품명·설명·가격을 검증하고 DB에 저장한다. |
| 상품 수정 | DB의 상품 정보를 변경하고 Redis에 남아 있는 이전 정보를 삭제한다. |
| 판매 중지 | 상품을 판매 불가 상태로 변경하고 관련 캐시를 삭제한다. |
| 상품 상세 조회 | Redis에 정보가 있으면 반환한다. 없으면 DB에서 조회한 뒤 만료시간을 지정해 Redis에 저장한다. |
| 상품 목록 조회 | DB에서 조건에 맞는 상품 목록을 페이지별로 조회한다. |

첫 캐시 적용 대상은 상품 상세 조회로 한다. 상품 목록 캐시는 검색 조건과 갱신 범위를 별도로 설계한 뒤 확장한다.

| 상황 | 처리 방안 |
|---|---|
| Redis 조회·저장 실패 | 정해진 시간 제한 후 DB 조회로 처리한다. |
| 상품 수정 후 캐시 삭제 실패 | 오류를 기록하고 재시도한다. 캐시 만료시간으로 이전 정보의 잔존 기간을 제한한다. |
| 존재하지 않는 상품 조회 | 상품이 없다는 결과를 반환한다. |
| 주문 시 가격·판매 상태 확인 | 캐시가 아닌 상품 원본을 기준으로 검증하는 내부 조회 경로를 사용한다. |

## 5. 주문 API 모듈

주문 접수와 조회를 담당한다. 재고 수량은 직접 변경하지 않는다.

| 기능 | 처리 내용 |
|---|---|
| 주문 접수 | 상품의 판매 상태·가격·주문 수량을 확인하고 주문을 처리 중으로 저장한다. |
| 주문 조회 | 본인의 주문 목록·상태·실패 사유를 반환한다. |
| 취소 요청 | 소유자와 취소 가능 상태를 확인하고 취소 처리 중으로 변경한다. |
| 관리자 조회 | 실패했거나 오랫동안 처리가 끝나지 않은 주문을 조회한다. |
| 중복 요청 확인 | 같은 주문 접수 요청을 다시 보내도 주문이 중복 생성되지 않도록 한다. |

주문 접수 시 주문 데이터와 재고 확보 요청을 Outbox에 같은 DB 트랜잭션으로 저장한다. 취소 접수 시에도 주문 상태 변경과 재고 반환 요청을 함께 저장한다.

주문에는 접수 시점의 상품명·단가·수량을 저장한다. 이후 상품 정보가 변경되더라도 기존 주문 내역은 유지한다.

| 상황 | 처리 방안 |
|---|---|
| 같은 접수 요청 재전송 | 중복 요청 식별값을 확인하고 기존 주문을 반환한다. |
| 상품 정보 확인 실패 | 주문 접수를 완료하지 않고 재시도 가능한 오류를 반환한다. |
| 판매 중지·잘못된 수량 | 주문 접수를 거절한다. |
| 취소 불가능 상태 | 취소 불가 사유를 반환한다. |
| 이미 취소 처리 중·취소 완료 | 재고 반환 요청을 중복 생성하지 않고 기존 상태를 반환한다. |

첫 구현에서는 확정된 주문만 취소할 수 있도록 하는 방안을 검토한다. 취소 가능 조건은 구현 전에 확정한다.

## 6. 주문 결과 처리 모듈

Kafka에서 재고 처리 결과를 받아 주문 상태를 변경한다.

| 받은 내용 | 처리 내용 |
|---|---|
| 재고 확보 성공 | 주문을 처리 중에서 확정으로 변경한다. |
| 재고 확보 실패 | 주문을 실패로 변경하고 사유를 저장한다. |
| 재고 반환 성공 | 주문을 취소 처리 중에서 취소 완료로 변경한다. |
| 재고 반환 실패 | 취소 완료로 변경하지 않고 재시도 또는 운영 확인 대상으로 남긴다. |
| 이미 처리한 결과 | 주문 상태를 중복 변경하지 않는다. |
| 현재 주문 상태와 맞지 않는 결과 | 상태를 강제로 덮어쓰지 않고 별도 확인 대상으로 기록한다. |

주문 상태 변경, 이벤트 처리 기록, 최종 결과 Outbox를 같은 DB 트랜잭션으로 저장한다.

DB 처리가 성공한 뒤 Kafka에 처리 완료 위치를 기록한다. 재시작으로 같은 결과를 다시 받더라도 처리 기록과 주문 상태를 확인해 중복 반영을 방지한다.

## 7. 주문 이벤트 발행 모듈

주문 DB의 Outbox를 읽어 Kafka로 전달한다. 주문 상태를 결정하거나 재고를 직접 변경하지 않는다.

| 기능 | 처리 내용 |
|---|---|
| 보낼 내용 조회 | 아직 전송하지 않았고 재시도 시각이 지난 내용을 조회한다. |
| 작업 확보 | 여러 실행 인스턴스가 같은 내용을 동시에 발행하지 않도록 처리 대상을 확보한다. |
| 내용 전달 | 재고 확보 요청·반환 요청·주문 최종 결과를 Kafka로 전송한다. |
| 성공 기록 | Kafka 전송 성공을 확인한 뒤 발행 완료로 표시한다. |
| 실패 시 재시도 | 오류·시도 횟수·다음 시도 시각을 기록하고 다시 전송한다. |
| 반복 실패 관리 | 내용을 삭제하지 않고 운영자가 확인하고 재처리할 수 있도록 남긴다. |

보낼 내용을 DB에 먼저 저장하는 이유는 주문 저장 후 Kafka 전달에 실패하더라도 나중에 다시 전달하기 위해서이다.

Kafka 전송 후 DB에 완료 표시를 하기 전에 중단되면 같은 내용이 다시 발행될 수 있다. 따라서 받는 모듈에서도 중복 처리를 방지한다.

## 8. 재고 API 모듈

관리자의 입고 등록과 재고 조회를 담당한다.

| 기능 | 처리 내용 |
|---|---|
| 입고 등록 | 관리자 권한과 수량을 검증한 뒤 재고를 증가시킨다. |
| 중복 입고 요청 확인 | 같은 입고 요청이 재전송돼도 수량을 두 번 증가시키지 않는다. |
| 재고 조회 | 전체 보유 수량·주문용 확보 수량·추가 주문 가능 수량을 반환한다. |
| 확보 내역 조회 | 어떤 주문에 몇 개를 확보했는지 조회한다. |

### 수량 구분

| 수량 | 의미 |
|---|---|
| 보유 수량 | 현재 보유한 전체 수량이다. |
| 예약 수량 | 주문용으로 확보한 수량이다. |
| 주문 가능 수량 | 보유 수량에서 예약 수량을 제외한 값이다. |

총 10개 중 주문용으로 3개를 확보했다면 추가 주문 가능 수량은 7개이다.

실제 출고 기능은 현재 범위에 포함하지 않는다. 출고 시 보유·예약 수량을 변경하는 방식은 후속 설계에서 정한다.

## 9. 재고 이벤트 처리 모듈

Kafka에서 재고 확보·반환 요청을 받아 처리한다.

| 받은 내용 | 처리 내용 |
|---|---|
| 재고 확보 요청 | 주문 수량이 남아 있는지 확인하고 해당 주문용으로 확보한다. |
| 재고 부족 | 수량을 확보하지 않고 실패 결과를 저장한다. |
| 여러 상품의 확보 요청 | 모든 상품을 확보할 수 있을 때만 함께 예약한다. 일부 상품만 예약하지 않는다. |
| 재고 반환 요청 | 해당 주문용으로 확보한 수량을 해제해 다시 주문 가능하게 변경한다. |
| 같은 요청 재수신 | 기존 처리 기록을 확인해 수량을 두 번 변경하지 않는다. |

여러 주문이 동시에 들어와도 남은 수량보다 많이 확보하지 않도록 DB에서 접근을 제어한다.

재고 변경, 처리 기록, 결과 Outbox를 같은 DB 트랜잭션으로 저장한다. DB 충돌이나 일시 장애는 재시도와 업무상 실패를 구분해 처리한다.

## 10. 재고 결과 발행 모듈

재고 DB의 Outbox에 저장된 결과를 Kafka로 전달한다.

| 기능 | 처리 내용 |
|---|---|
| 결과 조회 | 아직 전달하지 않은 재고 처리 결과를 조회한다. |
| 결과 전달 | 확보 성공·실패, 반환 성공·실패를 Kafka로 전송한다. |
| 성공 기록 | 전송 성공을 확인한 뒤 발행 완료로 표시한다. |
| 실패 시 재시도 | 오류와 재시도 정보를 기록한 뒤 다시 전송한다. |
| 재시작 후 처리 | 미완료 결과를 다시 조회해 처리한다. |

주문 이벤트 발행 모듈과 공통 코드를 재사용할 수 있다. 다만 접근하는 DB와 실행 단위는 분리한다.

## 11. 알림 API 모듈

DB에 저장된 사용자 알림을 조회하고 읽음 상태를 관리한다.

| 기능 | 처리 내용 |
|---|---|
| 알림 목록 조회 | 본인의 알림 목록을 최신순으로 반환한다. |
| 읽음 처리 | 알림 소유자를 확인한 뒤 읽음 상태로 변경한다. |
| 미확인 개수 조회 | 본인이 아직 읽지 않은 알림 수를 반환한다. |

다른 사용자의 알림을 조회하거나 수정할 수 없도록 소유권을 확인한다.

## 12. 알림 이벤트 처리 모듈

Kafka에서 주문 최종 결과를 받아 사용자 알림으로 저장한다.

| 받은 내용 | 처리 내용 |
|---|---|
| 주문 확정 | 주문 확정 알림을 저장한다. |
| 주문 실패 | 실패 사유를 포함한 알림을 저장한다. |
| 주문 취소 완료 | 주문 취소 완료 알림을 저장한다. |
| 같은 결과 재수신 | 기존 처리 기록을 확인해 같은 알림을 두 번 만들지 않는다. |
| 알림 저장 실패 | 오류를 기록하고 다시 처리한다. |

알림과 이벤트 처리 기록을 같은 DB 트랜잭션으로 저장한다. 저장에 성공한 뒤 Kafka에 처리 완료 위치를 기록한다.

## 13. 실행 단위를 나누는 이유

| 분리 대상 | 이유 |
|---|---|
| API와 백그라운드 처리 | 사용자 요청이 많을 때 API를 늘리고, 처리할 일이 밀릴 때 처리 모듈을 독립적으로 늘리기 위해서이다. |
| 업무 처리와 Kafka 전송 | 전달할 내용을 DB에 남기고 Kafka 연결이 복구된 뒤 다시 전송할 수 있도록 하기 위해서이다. |
| 상품·주문·재고·알림 | 데이터와 업무의 책임을 구분하고 독립적으로 변경·배포하기 위해서이다. |

## 14. 컨테이너 이미지와 배포 단위

| 컨테이너 이미지 | 해당 이미지로 실행할 모듈 |
|---|---|
| `product-service` | 상품 API |
| `order-service` | 주문 API, 주문 결과 처리, 주문 이벤트 발행 |
| `inventory-service` | 재고 API, 재고 이벤트 처리, 재고 결과 발행 |
| `notification-service` | 알림 API, 알림 이벤트 처리 |

서비스별 이미지 4개를 만들고 실행 명령을 구분해 Deployment 9개로 배포하는 구조이다.

Deployment 개수와 실제 Pod 개수는 다르다. 모듈별 복제 수, 자원, 상태 점검, 노드 분산과 확장 방식은 이후 Kubernetes 자원 설계에서 결정한다.
