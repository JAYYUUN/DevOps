## D-001. 계층형 README로 설계 관리

- 선택: 프로젝트 최상위 폴더는 `주문서비스/`. 요구사항·논리 설계·결정·진행을 하위 README로 나눕니다.
- 이유: 대화가 길어져도 담당 문서에서 내용을 찾고 다음 날 재개할 수 있도록 합니다.
- 제약: 같은 내용을 여러 문서에서 중복 관리하면 서로 달라질 수 있습니다.
- 대응: 내용은 담당 문서에서만 관리하고 상세 진행 상태는 progress에 모읍니다.
- 재검토 조건: 한 문서가 길어져 독립적인 하위 주제로 나눌 필요가 생길 때.

## D-002. 전체 논리 설계 후 구성 요소별 구현

- 선택: 요구사항 → 논리 설계 → 배치·자원 설계 → 구현·검증 순서로 진행합니다.
- 이유: 도구나 매니페스트가 먼저 정해져 서비스 요구사항을 끼워 맞추는 상황을 줄입니다.
- 제약: 이전 Terraform 초안을 최종 설계에 맞춰 수정하거나 교체할 수 있습니다.
- 대응: 검토 전에 파일·인프라 구성을 임의로 확정하지 않고 한 번에 한 주제씩 다룹니다.

## D-003. 데이터 계층의 배치와 운영 방식

- 선택지: 클라우드 관리형 / Kubernetes 내부 직접 운영 / 구성 요소별 혼합.
- 아직 정하지 않은 이유: 첫 범위·운영 학습 범위·예산·장애 기준을 먼저 정해야 합니다.
- 비교 기준: 운영 책임, 장애 영역, 노드·스토리지, 백업·복원, 인증·연결, 비용.
- 상태: 보류. 관리형 사용 또는 내부 배치 중 어느 쪽도 확정하지 않았습니다.

## D-004. 첫 구현 범위와 주문 확정 방식

- 제안: 상품 조회를 첫 흐름으로 완성하고 주문·재고·알림으로 확장.
- 주문 흐름 후보: 접수 후 비동기 확정 / 요청 중 재고 확인 후 확정.
- 필요한 결정: 사용자에게 응답할 시점, 처리 중 상태 허용 여부, 실패·취소 정책.
- 상태: 제안. [요구사항](../requirements/README.md) 검토 후 확정합니다.

## 참고 자료의 사용 방식

공식 문서는 기능·제약 확인에, 기업 사례는 작성 당시의 문제와 선택 이유를 이해하는 데 사용합니다. 사례의 선택을 그대로 우리 결정으로 간주하지 않습니다. 구현 시점에는 버전·설정의 현행성을 다시 확인합니다.

| 자료 | 참고할 주제 | 우리에게 아직 확정되지 않은 부분 |
|---|---|---|
| [카카오페이증권 플랫폼 운영](https://tech.kakaopay.com/post/kakaopaysec-devops-platform/) | 빌드·배포와 운영 플랫폼 | CI/CD 도구·구성·배치 |
| [카카오페이증권 Redis 운영](https://tech.kakaopay.com/post/kakaopaysec-redis-on-kubernetes/) | Kubernetes에서 데이터 계층 직접 운영 시 고려 사항 | Redis 내부 배치 여부 |
| [Grab Kafka 운영](https://engineering.grab.com/kafka-on-kubernetes) | Kafka 노드·스토리지·복구 설계 | 전용 노드·Kafka 직접 운영 여부 |
| [쏘카 MSK·ElastiCache 사례](https://aws.amazon.com/blogs/big-data/how-socar-handles-large-iot-data-with-amazon-msk-and-amazon-elasticache-for-redis/) | 애플리케이션과 관리형 데이터 계층 분리 | 관리형 사용 여부 |

세부 설계에 자료를 적용할 때 원문 작성 시점, 확인한 내용, 우리 조건과의 차이, 자체 판단을 해당 결정에 기록합니다.
