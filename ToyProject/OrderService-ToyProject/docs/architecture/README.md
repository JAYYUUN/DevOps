# 논리 설계

[프로젝트 처음으로](../../README.md) · [요구사항](../requirements/README.md) · [결정 기록](../decisions/README.md)

**상태: 구성 후보 정리. 서비스 경계·처리 정책은 미확정입니다.**

## 구성 요소의 책임 후보

| 구성 요소 | 책임 후보 | 데이터 소유권 후보 |
|---|---|---|
| 상품 | 상품 정보 관리·조회 | 상품 정보 |
| 주문 | 주문 접수·조회·최종 상태 관리 | 주문과 주문 상태 |
| 재고 | 재고 관리·예약·예약 해제 | 수량과 예약 내역 |
| 알림 | 최종 결과 알림 처리 | 처리 결과·전송 이력 |

이 표는 책임을 분리해 생각하기 위한 초안입니다. 각 항목을 반드시 독립 서비스나 Deployment로 만든다는 결정은 아닙니다. 특히 상품·재고 분리 여부와 초기 범위는 요구사항 합의 후 결정합니다.

## 데이터와 기술 역할 후보

| 기술 | 제안하는 역할 | 결정해야 할 내용 |
|---|---|---|
| MariaDB | 업무 원본과 트랜잭션 | 서비스별 소유권·계정·접근 방식·HA·백업 |
| Redis | 상품 조회 캐시 | 대상 데이터·TTL·무효화·장애 시 원본 보호 |
| Kafka | 주문·재고·알림의 비동기 이벤트 전달 | API 응답 시점·이벤트 명세·중복·재시도·순서·보관 |

원본 재고 판단은 DB 트랜잭션을 기준으로 하는 방안을 제안합니다. 캐시 조회값만으로 주문 가능 여부를 확정하지 않습니다. 정확한 정책은 결정 기록에서 검토합니다.

## 주요 흐름 초안

### 상품 조회

1. 상품 조회 요청을 받습니다.
2. 캐시를 적용했다면 Redis에서 조회합니다.
3. 캐시에 없으면 원본 DB에서 읽고 필요에 따라 캐시를 채웁니다.
4. 응답을 반환합니다.

검토할 실패: Redis 시간 초과, DB 장애, 상품 미존재, 상품 변경과 캐시 갱신 경합.

### 주문 처리

1. 주문 API가 접수 상태를 저장합니다.
2. 주문 이벤트를 Kafka로 전달합니다.
3. 재고 처리가 예약 성공·실패 결과를 전달합니다.
4. 주문이 최종 상태를 반영합니다.
5. 알림 처리가 최종 결과를 소비합니다.

이 흐름은 ‘접수 후 비동기 확정’을 선택하는 경우의 제안입니다. 즉시 확정 응답이 요구되면 흐름을 재설계합니다. DB 저장과 이벤트 발행의 일관성, 중복 소비, 예약 해제, 늦은 결과, 처리 기한과 재처리를 함께 설계해야 합니다. Outbox는 그중 검토할 후보입니다.

## 논리 설계에서 정할 관계

| 항목 | 기록할 내용 |
|---|---|
| API | 호출자·대상·요청·응답·오류·시간 제한 |
| 이벤트 | 발행자·소비자·의미·식별자·순서·중복·버전 |
| 데이터 | 원본·쓰기 주체·조회 경로·트랜잭션 경계 |
| 실패 | 부분 성공·중단·재시도·최종 실패·수동 복구 |

## Kubernetes 설계로 넘어갈 때

논리 흐름을 합의한 뒤 각 실행 단위별로 다음을 결정합니다.

| 영역 | 검토 질문 |
|---|---|
| 워크로드 | API·지속 Worker·일회성·정기 작업 중 무엇이며 어떤 자원이 맞는가? |
| Service·외부 진입 | 누가 접속하는가? Service와 외부 LB가 필요한가? |
| 복제·배치 | 동시 실행이 안전한가? 노드·AZ 분산과 여유 자원은 충분한가? |
| 상태 점검·종료 | Readiness·Liveness·Startup의 의미와 진행 중 작업 종료 방식은 무엇인가? |
| 자원·확장 | requests/limits와 확장 기준을 어떤 측정으로 정하는가? |
| 설정·권한·통신 | ConfigMap·Secret·ServiceAccount·IAM·통신 제한을 어떻게 적용하는가? |
| 관측·복구 | 무엇을 측정하고 어떤 상태에서 복구를 수행하는가? |

EKS Worker 2대와 데이터 계층의 고가용성은 별개의 문제입니다. 관리형 여부와 배치·복제·스토리지는 후속 배치 설계에서 확정합니다.
