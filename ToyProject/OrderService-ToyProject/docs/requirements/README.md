# 요구사항

[프로젝트 처음으로](../../README.md) · [문서 안내](../README.md) · [논리 설계](../architecture/README.md)

**상태: 검토 초안**

프로젝트 주제는 주문·재고·알림 시스템입니다. 아래 기능과 처리 정책은 기존 논의를 정리한 제안이며, 첫 구현 범위를 검토한 뒤 확정합니다.

## 사용자와 목적

| 사용자 | 제안하는 목적 |
|---|---|
| 주문 사용자 | 상품을 조회하고 주문을 접수한 뒤 결과 확인 |
| 상품·재고 관리자 | 상품 정보와 재고 관리 |
| 운영자 | 배포·처리 지연·오류를 확인하고 복구 |

회원 인증 방식과 사용자 화면의 범위는 미결입니다. 초기 API 문서 화면으로 요청할지, 별도 웹 화면을 만들지도 합의 후 정합니다.

## 기능 후보

| ID | 기능 | 기대 동작 초안 | 상태 |
|---|---|---|---|
| R-001 | 상품 조회 | 상품 정보 조회 | 제안 |
| R-002 | 상품·재고 관리 | 상품 정보와 재고 등록·변경 | 제안 |
| R-003 | 주문 접수 | 주문 ID와 접수 상태 반환 | 제안 |

| R-006 | 결과 알림 | 주문 최종 결과를 별도 처리 | 제안 |

## 첫 구현 범위

**제안:** 상품 조회 한 흐름부터 애플리케이션·배포·관측·장애 확인까지 완성한 뒤 주문 처리로 확장합니다.

- 먼저 합의할 것: 조회할 상품 필드, 초기 데이터 준비 방식, 요청·응답과 오류 형태.
- Redis 적용 시 비교할 것: 캐시 적용 전후 DB 조회량·응답 시간, 캐시 만료·갱신·장애 동작.
- 아직 정하지 않은 것: 측정 부하, 허용 응답 시간, 캐시가 오래된 값을 반환해도 되는 범위.

이 제안을 검토하기 전까지 상품 조회를 확정된 첫 범위로 취급하지 않습니다.

## 실패 시 기대 동작 후보

| ID | 상황 | 기대 동작 초안 | 미결 사항 |
|---|---|---|---|
| N-001 | API Pod 하나 종료 | 남은 인스턴스가 요청 처리 | 허용 오류·복구 시간 |
| N-002 | Worker Node 하나 중단 | 남은 노드에서 가능한 서비스 유지 | 필수 유지 기능·여유 자원 |
| N-003 | Redis 장애 | 짧은 시간 제한 후 원본 DB 조회로 전환 | DB 보호·접근 제한·허용 부하 |
| N-004 | Kafka 일시 장애 | 접수 이벤트를 보관하고 복구 후 전달 | 접수 지속 여부·보관·처리 기한 |
| N-005 | 이벤트 중복·Worker 재시작 | 같은 주문의 재고가 중복 반영되지 않음 | 멱등 처리와 재개 기준 |
| N-006 | 잘못된 버전 배포 | 감지 후 이전 정상 버전으로 복구 | 수동·자동 여부와 복구 기준 |

## 첫 범위에서 제외하는 방안

실제 결제 연동, 배송 연동, 복잡한 할인 정책, 멀티 리전·멀티 클러스터는 초기 범위에서 제외하는 방안을 제안합니다. 제외 여부도 범위 합의 시 기록합니다.

## 다음에 확정할 질문

1. 첫 사용자 흐름을 상품 조회로 시작할 것인가?
2. 그 흐름에 필요한 기능과 제외 기능은 무엇인가?
3. 정상·실패 응답을 어떤 결과로 정의할 것인가?
4. 어떤 측정과 장애 확인을 마치면 첫 범위가 완료됐다고 판단할 것인가?

요구사항이 확정되면 상태를 바꾸고 관련 논리 설계와 결정 기록에 연결합니다.
